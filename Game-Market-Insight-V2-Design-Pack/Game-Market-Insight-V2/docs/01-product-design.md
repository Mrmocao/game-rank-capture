# 游戏市场洞察平台 · 产品设计 V2.3

版本：2026-10-30｜评审稿｜适用正式技术方向：Java + MySQL Web 系统

## 1. 这次解决什么

从广泛的市场信息中发现值得团队验证的休闲游戏机会，每周给出少量、可解释、可行动的推荐。产品要回答：需求是否真实存在、为什么现在值得做、玩家到底喜欢什么、原作有哪些可改进之处、团队做得出来吗、下一步先验证什么。

“容易复刻爆款”落为“市场需求已有证据、核心机制可实现、团队成本可承受、存在差异空间的验证优先级”。系统不输出承诺收益或成功概率。借鉴玩法与需求，自行制作代码、美术、关卡和品牌素材。

本期优先顺序：信息范围与口径 → 评价/舆情分析 → 资格与周精选 → 产品交互与契约。具体数据供应商、采集方式、调度、费用、反爬适配与历史回补留到下一阶段。目录完整不等于所有字段已可获得。

## 2. 延续此前已确认的边界

| 项目 | 本版约定 |
| --- | --- |
| 核心平台 | 微信、抖音、iOS 中国；Google Play 先设美国、英国、德国、法国独立市场 |
| 中国市场与 GP | 中国市场主要由微信、抖音和 iOS 研究覆盖；本方案不设置 GP 中国大陆榜单。其他 GP 市场后续按配置扩展 |
| 变现范围 | 正式推荐仅纯 IAA，并且目标平台版本有依据；混变/未知产品可留作关联研究，不能混入合格推荐 |
| 发现频率 | 维持每天观察、核心榜单优先前 100；增加榜外发现、历史在榜、同类竞品、失败与下滑样本 |
| 入库 | 符合规则自动进入合格产品库；资格不明确进入观察池，保留缺口和补证任务 |
| 周报 | 默认目标 8 款，可配置 5～10；合格不足就少出，解释原因 |
| 历史 | 从系统上线积累。明确区分实际首发、系统首次观察、首次上榜；不编造此前历史 |
| 榜单 | 玩家热度和广告买量分开；平台/国家/榜单/日期独立；不存在跨榜平均名次 |
| 选用 | 同原产品可多人选用；每条记录有负责人、状态、日期、备注和验证反馈 |
| 流程 | 未选、已选、制作中、已完成、放弃；不增加复杂审批流 |
| 页面 | 保留蓝白企业后台风格，左侧“实际使用/配置管理”两级菜单 |

“未选”是某产品当前没有选用记录的派生状态。多条记录各有自己的状态；产品同时可能有“2 人已选、1 人制作中”，不能把多人状态压成单一字段。全部记录放弃时显示“历史选用，当前无进行中”，仍可重新选用。

## 3. 广覆盖的组织方式

以“产品 → 平台版本 → 地区/语言 → 时间窗口”为骨架，再关联玩法、开发/发行主体、广告创意、讨论主题与事件。相似玩法只是玩法家族关系，不等于同一游戏；相同名字不自动合并。跨平台对应关系需要证据和可撤销的合并记录。

信息分三层：广度层保留候选身份、市场快照、评价摘要、传播线索；分析层为增长、持续在榜、争议或被选用的产品补充玩法、评论主题和竞争结构；精选层为周报候选补齐 IAA、实机、成本、反对证据及最小验证方案。扩展范围和加深研究分开配置，避免每款游戏都做昂贵的全量视频分析。

| 信息域 | 核心问题 | 需要的主要内容 | 对推荐的作用 |
| --- | --- | --- | --- |
| 产品身份与生命周期 | 这是谁、哪个版本、何时出现 | ID、别名、主体、地区版本、上线/更新/下架、跨平台关系 | 去重、识别新发现、避免版本串线 |
| 榜单与市场表现 | 需求是否稳定或增长 | 各榜快照、进入退出、在榜天数、涨跌、下载/活跃估计及其口径 | 市场验证与机会时机 |
| 玩家评价与体验 | 玩家为什么喜欢或放弃 | 星级、计数、原文、日期、版本、主题、倾向、广告负担、重复内容 | 核心乐趣、问题与改进空间 |
| 社区舆情与讨论 | 是什么推动讨论 | 帖子/视频评论/论坛、提及、参与者、互动、转载簇、争议事件 | 识别自然讨论、营销线索与负面爆发 |
| 玩法与产品结构 | 机制是否可实现 | 核心循环、操作、规则、失败条件、关卡、外围系统、实机入口 | 制作适配与机制拆解 |
| 广告素材与投放 | 什么卖点吸引用户 | 创意变体、钩子、时长、投放地区/平台、活跃周期、落地版本 | 获客假设，不直接当作盈利证明 |
| 变现与经营线索 | IAA依据与体验如何 | 广告形式/触发、内购证据、去广告付费、版本有效期、授权经营数据 | 资格判定与变现风险 |
| 同类竞争与供给 | 还有没有进入空间 | 玩法家族、竞品密度、新增供给、头部集中、差异、失败样本 | 赛道拥挤度与差异化机会 |
| 传播、搜索与外部事件 | 热度是否外部事件造成 | 搜索趋势、话题、内容创作者、媒体、平台活动、季节性 | 解释趋势，避免把一次曝光当持续需求 |
| 内部能力与验证反馈 | 推荐对团队是否有用 | 人力/工期、资产复用、测试目标与结果、选用和放弃原因 | 个性化排序、持续校准 |

完整原子字段见 `02-information-catalog.csv`。字段带信息用途、优先级、口径和可得性；新增字段必须同时定义统计对象、时间、来源与缺失语义。

## 4. 广覆盖不能只有头部榜单

发现池同时容纳：核心 Top 100、曾经上榜仍被跟踪的项目、榜单外快速增长项目、玩法家族竞品、社区持续讨论项目、平台编辑推荐/活动线索、历史成功与后来下滑项目、内部人工补录项目。榜外线索先进入观察池，不因传播热度直接取得市场验证资格。

保留未入选、下架、下滑、停止投放、内部测试失败项目，用作比较和复盘。否则系统只能看到幸存者，容易夸大某类玩法成功率。定义范围时列出来源类别覆盖、地区/语言覆盖、完整率、已覆盖/待接入/受限/不适用状态；不使用无法证明的“全网覆盖率”。

中国研究覆盖中文反馈与本地版本；GP 研究按四个市场独立保留英文、德文、法文等原文和中文译文。语言、商店国家、发布位置、讨论者国籍是不同字段，不能相互推断。

## 5. 数据对象的生命周期

线索 → 观察池 → 合格候选库 → 周精选候选 → 推荐快照 → 选用/测试反馈。需要复核、暂不匹配和已关注动态是并行标签；资格变化不能抹掉历史。

正式入库需要身份明确、目标版本 IAA 有据、目标类型和市场匹配。验证清单在此之上要求需求与事件依据；分析或成本不全时可条件推荐，给出补证与投入限制。某版本变现改变时，从新生效日更新资格并提示以前推荐，保留旧周报当时结论。

## 6. 本版可验证的产品目标

研究者能从推荐卡在两次下钻内到达证据；选定日期后所有市场快照受该日约束；未观察到与未上榜可区分；所有精选说明反对/未知项；评价页面显示分母、样本范围与时间；高热负面案例被识别为复核；同款多人选用互不覆盖。

本期不定义全网抓取承诺、模型预测收益、无人监督自动采购数据、复杂审批或重型项目管理。

## V2.2：不等资料齐全才服务研究者

每个已知候选都有结论和行动：重点验证、条件推荐、线索推荐、暂缓或范围不匹配。软指标缺失使用范围，不补0、不填50、不按单个产品重分权重。资料不足时可先做低成本研究；IAA未知仍不正式作为纯IAA合格产品入库。完整信息目录不等于每次推荐的必填表。

每周清单允许条件推荐组成全期；没有验证合格项时输出线索与补证报告，不制造成功判断。新增可靠材料可升级或撤销推荐。更广覆盖不保证更高准确性，质量、相关性和真实反馈同样必要。具体规则、计算和补证优先级见14，18例演算见15。


## V2.3 单款档案覆盖条款

当前单款游戏信息设计以17、18、19章为准：12信息域、81展示字段、8分区，平台/市场/版本/截止时间独立；来源事实与AI草案分别保存。完整资料量不等于推荐分，缺失和新反证不能被填补文案掩盖。V2.2推荐公式与分层规则保持不变。
